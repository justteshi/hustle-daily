# Hustle Daily

Private, multi-user health and nutrition tracker for desktop web and iPhone. Each person has their own account and isolated foods, recipes, meals and health data. The web food catalogue, recipe editor and food history are available; targets and mobile parity remain ahead. HealthKit, notifications and private iOS signing come later.

## Local setup

Requirements: Docker Compose, Node 24, npm, and an iPhone development environment for the mobile app. PostgreSQL and Redis run in Docker; no database server is installed directly on the host. Copy `.env.example` to the repository-root `.env`, set a strong `DB_PASSWORD` and `APP_KEY`, and configure your HTTPS hostname. The root `.env` is the one Docker Compose reads; a key in `backend/.env` does not automatically configure the containers. To generate a key, build the API with `docker compose build api`, then run `docker compose run --rm --no-deps api php artisan key:generate --show` and paste the result into the root `.env`. Do not commit either `.env` file.

The default stack uses persistent Docker named volumes for PostgreSQL and Redis. Run `make up`, then `make migrate`. Create the first admin with `make user EMAIL=you@example.com`; the command prompts for a name and password. `/admin` is the Filament panel. A regular user can be created with `docker compose exec -it api php artisan hustle:create-user user@example.com`. `make down` stops containers but keeps the data; do not use `docker compose down -v` unless you intentionally want to delete the named volumes.

The user-facing web app is served at `/` through Caddy, separate from `/admin`. It supports browser-session login, today's food totals, searchable branded foods, food and portion editing, reusable recipe creation/editing, logging ready meals or individual ingredients, and browsing food history to correct past meals. Existing meal corrections are audited, and catalogue edits and retries use idempotency keys. Historical consumption snapshots do not change when a food or recipe definition is edited. History currently covers food entries only; day summaries and HealthKit data come later. The web bundle is built inside the Caddy image by `make up`; to develop locally run `cd web && npm ci && npm run dev`. The Vite proxy uses `VITE_DEV_BACKEND_URL` (default `https://localhost`) and verifies TLS certificates; trust your local Caddy certificate on the development machine rather than disabling verification.

The optional `make up-ephemeral` command is only for disposable tests; it uses a separate Compose project and memory-only PostgreSQL/Redis storage. Do not use it for data you want to keep. Stop it with `make down-ephemeral`. With `APP_DOMAIN=localhost`, Caddy serves local HTTPS, but an iPhone still needs a real HTTPS hostname and trusted certificate.

The mobile project reads `EXPO_PUBLIC_API_BASE_URL` at build time (for example `https://your-domain/api/v1`). Run `cd mobile && npm ci && npx expo start --dev-client`. Expo Go is not supported. An iOS development build and registered device signing are needed; the physical-device HealthKit module and EAS ad hoc distribution are later milestones. No Apple identifier is included here. The Phase 2 app has login, a consumed-calorie Today view, private food search/creation, and multi-food meal logging. It does not cache writes offline; failed requests can be retried with the same idempotency key.

## Development checks

Create a dedicated test database once with `docker compose exec -T db createdb -U hustle_daily -O hustle_daily hustle_daily_test` (adjust the username if changed). Run `make test`, `make lint`, and `make openapi`. `docs/openapi.json` is generated from Laravel routes by Scramble. `docker compose ps` shows API, database, Redis, worker and scheduler health. Docker services do not expose PostgreSQL or Redis ports. Caddy obtains HTTPS certificates for the configured hostname.

API endpoints: `POST /api/v1/auth/login` accepts email, password and device_name; `GET /api/v1/me` and `POST /api/v1/auth/logout` require a bearer token. Phase 2 adds private foods, meal categories, recipes, consumptions, and `GET /api/v1/dashboard/today`. Recipe logging expands branded ingredients into immutable nutrition snapshots. All nutrition values come from app food records, never HealthKit. Mutations require an `Idempotency-Key` header. Errors use an `error` object with code, message, details and request_id. Responses include `X-Request-ID`. See `docs/openapi.json` for request schemas.

The `/admin` panel works for accounts created with `--admin`. Admins can create/edit foods, nutrition, explicit food portions, meal categories, and saved recipes with branded ingredients. Existing users and their locale/time-zone settings can be edited; new accounts are still created through the safe CLI command. Past consumption snapshots are intentionally not rewritten when catalogue entries change. The Consumptions admin page can correct a past log's category or notes without recalculating nutrition, or replace all its ingredients to recalculate from current food values. Every correction requires a reason and stores before/after snapshots in a read-only Consumption Revisions list. Older custom portions must be reselected explicitly; the app never guesses a conversion. Health records, targets and daily summaries need dedicated admin workflows in later phases. Regular users cannot access the panel.

The database is server authoritative. Web login uses a server-side cookie session with CSRF protection; mobile still uses Sanctum tokens. There is no public registration or offline write queue. See [architecture](docs/architecture.md) and the ADRs for the planned domain boundaries.
